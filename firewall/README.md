# Backend Firewall Isolation — Mac 3 and Mac 4 — Phase 2 Extension C

Restricts TCP 3001 / 3002 so that **only the edge (Mac 2)** can reach the
backends. A client machine must not be able to connect to them directly.

## Files

| File | What it is |
|---|---|
| `pf.anchors.cn-backend.template` | the rules, with `<MAC2_IP>` to be filled in |
| `pf.anchors.cn-backend` | generated by `./scripts/set-ips.sh` — install to `/etc/pf.anchors/` |
| `pf-cn.conf` | main ruleset: macOS defaults **plus** our anchor |
| `enable-isolation.sh` | snapshot → install → dry-run → load → show |
| `disable-isolation.sh` | restore the stock ruleset and the original pf state |
| `rollback/` | created automatically; holds the pre-demo snapshot |

## Use

```bash
./scripts/set-ips.sh
./firewall/enable-isolation.sh          # on Mac 3 and Mac 4 (needs sudo)
./scripts/test-isolation.sh             # from a CLIENT, e.g. Mac 1
./firewall/disable-isolation.sh         # roll back when done
```

## Two things that will be asked

**Why a separate `pf-cn.conf` instead of just loading the anchor?**
Rules inside a pf anchor are only evaluated if the *main* ruleset references that
anchor. macOS's `/etc/pf.conf` references only Apple's anchor, so loading ours
with `pfctl -a cn-backend -f` alone would install rules that never run.
`pf-cn.conf` is the macOS default ruleset plus our anchor reference.

**Why `block drop` and not `block return`?**
`drop` discards silently, so the client sees a **timeout**. `return` sends a TCP
RST, so the client sees **connection refused**. Refused means nothing is
listening; timeout means something is filtering you. Real firewalls drop, and the
distinction is a diagnostic tool we use in `scripts/diagnose.sh`.

**Rule order matters.** `quick` means first match wins, so the `pass` rules for
localhost and the edge must come *before* the `block` rules. Reversed, you would
lock out nginx along with everyone else.
