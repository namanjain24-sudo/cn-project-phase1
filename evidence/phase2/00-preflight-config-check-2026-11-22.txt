---------------------------------------------------------------------------
5. TASK F CACHING — 200 then 304
---------------------------------------------------------------------------
$ ./scripts/test-cache.sh http://localhost:3001
  HTTP/1.1 200 OK        X-Backend: A  Cache-Control: max-age=60
                         ETag: "da4313339d3554937c06860be7d7e754e3b18bcf"
  HTTP/1.1 304 Not Modified   (same ETag, no body)

Two bugs fixed in this script, both of which bit us on camera in Phase 1:
  - it used `curl -sI`, which sends a HEAD request. The backends only route GET,
    so HEAD fell through to the 404 handler. That is the same reason the Phase 1
    video showed "HTTP/2 404" for curl -I. Now uses -D- -o /dev/null (a GET that
    prints headers).
  - in the video the ETag was pasted WITHOUT the "If-None-Match:" header name,
    so the server answered 200 while the narration said 304. The script builds
    the header correctly; use the script rather than retyping by hand.

Run against ONE backend, not the domain: /api/data's body contains the backend
id, so A and B hash to different ETags and a conditional request that round-robins
to the other backend correctly returns 200. That is caching working as specified.

---------------------------------------------------------------------------
6. EXT D — THE HEADLINE MEASUREMENT
---------------------------------------------------------------------------
Backend A was replaced with a process that ACCEPTS the TCP connection and then
never answers -- the software equivalent of Akshay's laptop sleeping mid-demo in
Phase 1. One identical request through each edge configuration:

  PHASE 1 config (nginx defaults)          HTTP 200 after  60.012 s
  PHASE 2 config (max_fails + timeouts)    HTTP 200 after   0.004 s

Burst of 6 with A still hung:
  1  Backend B  200   3008ms   <- paid proxy_read_timeout (3s), retried on B
  2  Backend B  200      3ms
  3  Backend B  200   3005ms   <- second failure, max_fails=2 reached
  4  Backend B  200      3ms   <- A ejected for fail_timeout=10s
  5  Backend B  200      3ms
  6  Backend B  200      3ms
  A=0  B=6  failed=0

Exactly two slow requests, then the dead backend is removed from the pool.
ZERO client-visible errors. A CLEANLY stopped backend (connection refused rather
than hung) fails over with no measurable delay at all -- worst latency 4ms --
because a refusal is instant whereas a hang must be waited out. That difference
is the whole lesson of this extension.

10. BUGS FOUND BY RUNNING THE TOOLING (not by reading it)
---------------------------------------------------------------------------
  a) Three scripts treated dig's ERROR TEXT as a valid answer, so a dead
     resolver reported as healthy -- the most dangerous kind of bug here,
     because the Ext A demo would have looked like it passed. Now only a
     dotted-quad counts as an answer.
  b) diagnose.sh hard-coded port 443, so any team using the permitted 8443
     fallback would see a false "connection refused".
  c) dns-cutover.sh used `sed s|...|...|` while its own pattern contained the
     alternation (app|api). The delimiter collided and the rewrite silently
     failed while the script reported success. Changed to s#...#...#.
  d) test-cache.sh sent HEAD (curl -I) to backends that only route GET, so it
     always 404'd -- the same 404 visible in the Phase 1 video.
  e) Temp files were written to /tmp with $$ and failed under a restricted
     TMPDIR; switched to mktemp.
  f) config/ips.env overrode environment variables instead of the reverse.
  g) test-ha-failover.sh blamed proxy_connect_timeout for a delay actually
     caused by proxy_read_timeout. A confidently wrong explanation is worse
     than none in a viva, so it now distinguishes the two.
  h) set-ips.sh regenerated the PHASE 1 configs from their templates, replacing
     their real provenance comments with placeholder boilerplate. Those files
     are a graded deliverable, so it now rewrites only the IP values in place.
