Mac 1 is the honest tester here: it is neither the edge nor a backend, so it
has no privileged path to ports 3001/3002.

Rules loaded on Mac 3 and Mac 4 by ./firewall/enable-isolation.sh (FINAL set):
    pass  in quick inet proto tcp from 127.0.0.1   to any port = 3001
    pass  in quick inet proto tcp from 127.0.0.1   to any port = 3002
    pass  in quick inet proto tcp from 10.7.11.169 to any port = 3001   # Mac 2, primary edge
    pass  in quick inet proto tcp from 10.7.11.169 to any port = 3002   # Mac 2, primary edge
    pass  in quick inet proto tcp from 10.7.21.130 to any port = 3001   # Mac 4, standby edge
    pass  in quick inet proto tcp from 10.7.21.130 to any port = 3002   # Mac 4, standby edge
    block drop in quick proto tcp from any to any port = 3001
    block drop in quick proto tcp from any to any port = 3002

  NOTE ON THE SCREENSHOTS 01 and 02: those were taken at the FIRST load, when
  the rules allowed only Mac 2. They are kept because they show the loader doing
  its job -- snapshot, dry run, load, print. The standby edge (10.7.21.130) was
  added immediately afterwards and the rules were reloaded on both machines;
  see 'EXTENSION C vs EXTENSION E' below for why.

  Rule ORDER matters: 'quick' means first
  match wins, so the pass rules must precede the block rules. Reversed, the
  block would win and nginx itself would be locked out along with everyone else.

TIMEOUT vs REFUSED -- the detail worth stating in the viva
  These probes TIME OUT, they are not refused. We used 'block drop', which
  discards the packet silently, so the client waits and gives up. 'block
  return' would have sent a TCP RST and the client would have seen
  'connection refused' instantly.
    refused = the host is up and nothing is listening on that port
    timeout = something is filtering the packets
  Earlier today the SAME probe to Backend A returned 'refused' when the node
  process had been killed. Same port, same host, different symptom, different
  cause -- that distinction is what makes the Extension F diagnosis work.

  Mac 3 is MDM-managed and refused changes to the macOS Application Firewall
  from the command line. pf is a different subsystem and was NOT restricted,
  so Extension C worked there regardless. Two separate firewalls on macOS:
  socketfilterfw (per-application) and pf (per-packet). This extension uses pf.

---------------------------------------------------------------------------
EXTENSION C vs EXTENSION E — a conflict caught before it bit us
---------------------------------------------------------------------------
The first version of these rules allowed only Mac 2 to reach the backend ports.
That is correct exactly until Extension E moves the edge. The moment the DNS
record pointed at the standby on Mac 4, the standby would have been firewalled
out of BOTH backends and would have returned 502 for everything -- while the
firewall itself looked perfectly healthy and the backends were perfectly fine.

This was caught by reasoning about the rules before running the cutover, not by
hitting the failure. The fix was to allow the EDGE TIER rather than one host,
which is how a real security group is written: it permits the load-balancer
tier, not one specific load balancer.

Re-verified after the change, from Mac 1:
  - Backend A 10.7.25.47:3001   -> still TIMES OUT from a client
  - Backend B 10.7.21.130:3002  -> still TIMES OUT from a client
  - https://app.cn_team.test/   -> still 200 through the primary edge
  - standby edge on Mac 4       -> able to reach the backends (HTTP/2 200)

Both extensions now hold at the same time.
